Concepts and methods

The ideas behind the drawings and how they were made. docs/architecture.md

Fjordvik's architecture is described in 25 drawings across four documents: this one, the data model, the requirements and the threat model. Each drawing answers one question for one kind of reader, at one level of detail. This section explains the ideas behind them and how they were made, so the drawings can be read without prior knowledge of the notations.

Every external system in the drawings is simulated: the data generator in data writes what each one would send, in its shape.

The C4 model

The C4 model, created by Simon Brown (c4model.com), describes software at four zoom levels, like a map: context (the whole system as one box, with its users and neighbouring systems), containers (the applications and data stores inside it), components (the building blocks inside one container) and code (classes and functions). Fjordvik draws the first three. The code level is left out, as the C4 guidance suggests, because the code itself shows it more accurately. A reader with two minutes looks at level 1; someone working on one part goes down to level 3.

Data flow diagrams

A data flow diagram follows data rather than systems. It uses four elements: an external entity (who owns and sends the data), a process (a step that moves or changes it, numbered P1 to P11), a data store (where it rests) and a data flow (a labelled arrow). Its one strict rule is that data always passes through a process: it never moves straight from an owner to a table, or from one table to another. Level 1 means each process is shown as one step, without its inner detail.

Data models and star schemas

The tables follow a star schema, the design Microsoft recommends for Power BI: each fact table records events to add up (sales, readings, emissions) and sits in the middle of a star of dimension tables, the things facts are filtered and grouped by (month, site, product). Each fact table has a stated grain: what one row holds, such as "one row per month, site and source". A primary key (PK) picks out exactly one row of a table; a foreign key (FK) holds the key of a row in another table, so the two can be joined. The lines use crow's foot notation: two short bars mean exactly one row, and a circle with three prongs means zero, one or many. Every line therefore reads "one row here matches any number of rows there".

Trust boundaries

A trust boundary is where data or control passes between parties that trust each other to different degrees, for example from a site's spreadsheet into the platform, or from Claude into the connector. Threat modelling guidance from OWASP (the Open Worldwide Application Security Project) and Microsoft draws each zone of equal trust inside a dashed line; every arrow that crosses a line is a point to check. The threat model checks each crossing against STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege.

The status word is written in every box, so the drawings read in black and white. Every box names its type and technology in square brackets, and every line says what it does in the direction it points.

How the drawings were made

  • Written as text. Each drawing is written in Mermaid, a text format that GitHub draws inside Markdown files. The drawings live in the repository beside the code, change through the same review as the code, and keep a full history.
  • Checked against the C4 checklist. Each drawing has a title stating its type and scope, a key, the type and technology of every box, a label on every line that matches its direction, and every abbreviation explained.
  • Laid out to be read. Keys sit in a table under each drawing rather than inside it, which keeps the drawings narrow. Wide drawings were reorganised to read at page width where possible, and crossing lines were kept to a minimum, because crossings are the layout feature that most harms understanding (Purchase, 1997, a peer-reviewed study of how people read graphs). Only two line styles are used, on purpose: Mermaid can give a single line its own style only by its position number, which breaks unseen when a line is added.
  • Readable without sight. Each drawing carries a short title and description for screen readers, as the Web Content Accessibility Guidelines (WCAG) 2.2 require for images.
  • Kept current. The context and container drawings are the intended design: they change only through a decision record, in the same change as the code. The data model drawings are generated from the tables' column headers by a script, so they match the tables. Under each drawing, "Last updated" gives the date it was last revised and the commit of the code and data it was checked against.
